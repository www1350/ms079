## P0：封包破坏 — 必须立即修复

### P0-1：isBodySlot/isCashSlot 边界 off-by-one

**文件**：`constants/EquipSlot.java`

**问题**：`BODY_SLOT_MIN = -99`，`isBodySlot(pos)` 条件为 `pos < 0 && pos > -99`，导致 pos=-99 时返回 false。原始代码 `pos > -100` 对 -99 返回 true。-99 槽位装备从 body 段错移到 cash 段，封包字段错位，客户端 ACCESS_VIOLATION。

**修复**：

```java
// 方案B（推荐）：改条件，不改常量值
// 保持 BODY_SLOT_MIN = -99 语义不变，避免影响 MapleInventoryManipulator:818 的 dst < BODY_SLOT_MIN 比较
public static boolean isBodySlot(int pos) {
    return pos < 0 && pos >= BODY_SLOT_MIN;  // -99 <= pos < 0
}
public static boolean isCashSlot(int pos) {
    return pos < BODY_SLOT_MIN && pos > BLOCKED_BOUNDARY;  // -100 <= pos <= -999
}
```

> **Review 修正**：不采用方案A（`BODY_SLOT_MIN = -100`），因为 `MapleInventoryManipulator.java:818` 有 `dst < EquipSlot.BODY_SLOT_MIN` 的范围比较，改为 -100 后 -100 槽位不再被现金装备校验条件覆盖，引入新漏洞。

**验证**：修复后逐个测试 -99, -100, -101, -1, -999, -1000 的分类结果，确认与原始魔数逻辑一致。

## P1：数据安全与并发 — 本迭代修复

### P1-1：DirtyTracker 线程安全

**文件**：`client/DirtyTracker.java`

**问题**：`EnumSet` 非线程安全。`mark()` 从 IO/Timer/Actor 多线程调用，`isDirty()+clear()` 在 saveToDB 线程，存在 ConcurrentModificationException 和脏标记丢失风险。

**修复**：

```java
public final class DirtyTracker {
    private final ConcurrentHashMap<Category, Boolean> dirty = new ConcurrentHashMap<>();

    public void mark(Category category) {
        dirty.put(category, Boolean.TRUE);
    }

    public boolean isDirty(Category category) {
        return dirty.containsKey(category);
    }

    public void clear() {
        dirty.clear();
    }

    public boolean hasAnyDirty() {
        return !dirty.isEmpty();
    }
}
```

> **Review 补充**：`clear()` 与 `mark()` 之间存在语义竞态——如果 `clear()` 执行期间有 `mark(X)` 发生，X 可能被清除也可能保留。这是"最终一致"的：丢失的 mark 会在下一次变更时重新设置，最坏情况是某次 saveToDB 少保存一个脏类别，下次 auto-save 会补救。根本解决需等 P2-2（saveToDB 迁移到 actor）。

### P1-3：CharacterBuffs 多方法缺 actor 保护

**文件**：`client/component/CharacterBuffs.java`

**问题**：以下公开方法直接操作 `effects` map 和发送封包，未用 `owner.getActor().execute()` 包裹：

| 方法 | 调用来源 | 风险 |
|------|---------|------|
| `cancelBuffStats` | PlayerHandler, changeJob, unequip (IO线程) | 中：直接操作 effects + 发封包 |
| `cancelEffectFromBuffStat` | PlayerHandler, SummonHandler, doRecovery(Timer) | 高：effects.get 可读到不一致状态 |
| `handleEnergyCharge` | PlayerHandler (IO线程) | 高：修改 effects + 发封包 + Timer 回调 |
| `handleBattleshipHP` | PlayerHandler (IO线程) | 高：修改 battleshipHP + dispelSkill |
| `handleOrbgain` | PlayerHandler (IO线程) | 高：读+修改 effects + 发封包 |
| `handleOrbconsume` | PlayerHandler (IO线程) | 高：读+修改 effects + 发封包 |
| `setBuffedValue` | Timer回调(间接), handleEnergyCharge(内部) | 中：修改 effects value |

**修复原则**：所有修改 `effects` map 或发送封包的方法，必须在 actor 上执行。

```java
// 辅助方法，避免每个公开方法都写 owner.getActor().execute()
private void onActor(Runnable task) {
    owner.getActor().execute(task);
}

// 示例：cancelBuffStats
public void cancelBuffStats(MapleBuffStat... stat) {
    onActor(() -> {
        List<MapleBuffStat> buffStatList = Arrays.asList(stat);
        deregisterBuffStats(buffStatList);
        cancelPlayerBuffs(buffStatList);
    });
}

// 示例：setBuffedValue
public void setBuffedValue(MapleBuffStat stat, int value) {
    onActor(() -> {
        if (effects.containsKey(stat)) {
            effects.get(stat).value = value;
        }
    });
}
```

**死锁分析**：`PlayerActorExecutor.execute()` 有 inline 检测（已在 actor 线程则直接执行），嵌套调用不会死锁。跨 player 的 execute 死锁风险本身存在但不因本次修改增大。

**需关注的间接调用链**：
- `cancelEffectFromBuffStat` → `cancelEffect`（已有 execute）：整段包在 execute 后，cancelEffect 会 inline 执行，无问题
- `handleBattleshipHP` → `dispelSkill` → `cancelEffect`（已有 execute）：同样 inline，无死锁
- `handleEnergyCharge` 中 `Timer.BUFF.schedule(() -> setBuffedValue(...))`：Timer 回调从 Timer 线程调用，setBuffedValue 包了 execute 后正常排队，无死锁

**已知局限**：`dispel()`、`dispelSkill()`、`cancelAllBuffs()` 也直接 iterate effects 并调用 cancelEffect。cancelEffect 自身有 execute 保护，但 iterate 部分没有保护。ConcurrentEnumMap 的弱一致迭代在大多数情况下安全，建议标注为已知局限，在 P2-2 中统一解决。

### P1-4：DParty JOIN/LEAVE 未持久化 party 字段

**文件**：`com.github.mrzhqiang.maplestory.service.PartyService`

**问题**：`updateParty()` 中 JOIN/LEAVE/EXPEL 操作仅修改内存中的 `MapleParty`，未同步更新 `DCharacter.party` 字段。崩溃恢复后 init() 通过 `QDCharacter.party.eq(dp.getId())` 查成员，查不到 JOIN 后未刷盘的成员。

**修复**：

```java
case JOIN:
    party.addMember(target);
    DB.update(DCharacter.class)
        .set("party", party.getId())
        .where().idEq(target.getId())
        .update();
    break;

case LEAVE:
case EXPEL:
    party.removeMember(target);
    DB.update(DCharacter.class)
        .set("party", -1)
        .where().idEq(leaver.getId())
        .update();
    break;
```

> **Review 补充**：`disbandParty()` 也需增加批量清理：
> ```java
> public void disbandParty(int partyid) {
>     DB.update(DCharacter.class)
>         .set("party", -1)
>         .where().eq("party", partyid)
>         .update();
>     DB.delete(DParty.class, partyid);
>     cached.invalidate(partyid);
> }
> ```
> 否则 DCharacter.party 仍指向已删除的 party ID。

**性能评估**：每次 JOIN/LEAVE 做一次单行 UPDATE（主键查询），亚毫秒级，不会成为瓶颈。

## P2：架构健壮性 — 下个迭代修复

### P2-1：组件暴露可变内部集合

**问题**：6 个组件暴露了可变内部集合，外部可绕过 actor 和 dirtyTracker 直接修改状态。

| 组件 | 泄漏方法 | 类型 |
|------|---------|------|
| CharacterSkills | `getSkillsInternal()` | ConcurrentHashMap（可变） |
| CharacterSkills | `getMacros()` / `getRemainingSps()` | 数组（可直接修改元素） |
| CharacterQuests | `getQuestMapInternal()` / `getInfoQuestMapInternal()` | LinkedHashMap（可变） |
| CharacterBuffs | `getEffectsInternal()` | ConcurrentEnumMap（可变） |
| CharacterCooldowns | `getCoolDownsMap()` | ConcurrentHashMap（可变） |
| CharacterPets | `getPets()` | ArrayList（可变） |

**修复方案**：分两步走。

**Step 1（本迭代）**：添加只读视图方法，标记 Internal 方法为 `@Deprecated`：

```java
@Deprecated // 仅用于 saveToDB，后续应改为组件自管保存
public Map<ISkill, SkillEntry> getSkillsInternal() { return skills; }

// 新增只读视图
public Map<ISkill, SkillEntry> getSkills() {
    return Collections.unmodifiableMap(skills);
}
```

**Step 2（下迭代）**：将 saveToDB 中的直接集合访问改为组件自管的 `saveSkills()` 方法，消除 Internal getter。

### P2-2：playerLock 与 Actor 并存清理

**问题**：MapleCharacter 同时使用 `playerLock`（显式锁，~20 处使用）和 `actor`（单线程队列），两种并发模型混用易死锁。

**修复路线**：
1. 短期：在 `saveToDB()` 中改用 `actor.execute()` 替代 `playerLock.lock()`，消除锁嵌套风险
2. 中期：逐一消除 `playerLock` 的使用点，全部迁移到 actor 模型
3. 长期：删除 `playerLock` 字段

**前提**：P1-3 完成后（所有组件方法都在 actor 上执行），saveToDB 才能安全地用 `actor.execute()`。

> **Review 补充**：saveToDB 包含 DB 事务，如果 DB 响应慢，`execute()` 会阻塞 actor 线程，导致该玩家所有封包处理暂停、定时器回调堆积。建议分两步：
> 1. 先用 `actor.execute()` 保证线程安全（当前阶段）
> 2. 后续优化为 `actor.submit()` + `drainDirty()` 原子取出脏集合，避免阻塞 actor

### P2-3：MapleMap hurtTask 同步

**文件**：`server/maps/MapleMap.java`

**问题**：`startHurtTask()`/`cancelHurtTask()` 无同步保护，并发 addPlayer/removePlayer 可导致泄漏或丢失。

**修复**：

```java
private final Object hurtTaskLock = new Object();

private void startHurtTask() {
    synchronized (hurtTaskLock) {
        if (hurtTask != null || decHP <= 0) {
            return;
        }
        final int interval = Math.max(decHPInterval, 1000);
        hurtTask = Timer.MAP.register(() -> {
            if (getCharactersSize() == 0) {
                cancelHurtTask();
                return;
            }
            for (MapleCharacter chr : getCharactersThreadsafe()) {
                if (!chr.isAlive()) continue;
                if (chr.getInventory(MapleInventoryType.EQUIPPED).findById(protectItem) != null) continue;
                if (mapid == 749040100 && chr.getInventory(MapleInventoryType.CASH).findById(5451000) != null) continue;
                chr.getActor().submit(() -> chr.addHP(-decHP));
            }
        }, interval, interval);
    }
}

private void cancelHurtTask() {
    synchronized (hurtTaskLock) {
        if (hurtTask != null) {
            hurtTask.cancel(false);
            hurtTask = null;
        }
    }
}
```
