# 优化机会分析

> 2026-05 Phase 4C（异步持久化）放弃后的替代优化方向分析

---

## 一、总体判断

Phase 4C 放弃了是对的——异步持久化有快照开销、失败无法恢复、断线时序问题和低收益四个现实问题。加上 Phase 3 的 DirtyTracker 已经把 saveToDB 从 12 张表全量删插降到了 1-2 张表变更，异步化的边际收益极低。

本分析聚焦**低风险、独立可验证、有实际感知收益**的优化项。

---

## 二、Top 3 优化项

### 1. 传送门脚本缓存修复 — 最高优先级

**文件：** `scripting/PortalScriptManager.java:57-59`

**问题：**

```java
if (scripts.containsKey(scriptName)) {
    scripts.clear();                        // ← BUG: 清空整个缓存
    return scripts.get(scriptName);         //     返回 null（刚清空）
}
```

原意应该是"命中缓存直接返回"，但 `scripts.clear()` 把缓存全清了，导致每次穿过任一传送门，所有缓存丢失。之后每个新传送门都要重新执行：`JSoup 解析 XML` → `Nashorn 编译` → `eval()` → `getInterface()`。

**数据：** 765 个传送门脚本（`脚本/传送点/`），Nashorn 编译一个 JS 脚本的耗时约 5-15ms。无缓存时每个新传送门首次穿过有 5-15ms 延迟。

**修复：**

```java
if (scripts.containsKey(scriptName)) {
    return scripts.get(scriptName);         // 直接返回缓存
}
```

**影响：** 1 行改动，消除所有传送门脚本的重复编译。传送点穿过的响应延迟从 5-15ms 降到 < 1ms（直接调 `enter()` 方法）。

**风险：** 极低。没有任何理由在"命中缓存"时清空缓存。这是明显的 typo 或误解。

### 2. 封包分派 O(n) → O(1)

**文件：** `handling/MapleServerHandler.java:430-432`

**问题：**

```java
for (RecvPacketOpcode recv : RecvPacketOpcode.values()) {
    if (recv.getValue() == header_num) {
        // ... 处理
    }
}
```

每个收到的封包都遍历 `RecvPacketOpcode.values()` 数组做线性匹配。枚举值约有 90+ 个。虽然单次遍历成本低（~90 次引用比较），但这是每个封包的必经路径——玩家移动、攻击、拾取等高频操作每帧都可能触发多次。

**修复：**

```java
// 在 MapleServerHandler 初始化时建立索引
private static final Map<Short, RecvPacketOpcode> OPCODE_MAP = 
    new HashMap<>();
static {
    for (RecvPacketOpcode opcode : RecvPacketOpcode.values()) {
        OPCODE_MAP.put(opcode.getValue(), opcode);
    }
}

// 替换循环：
RecvPacketOpcode recv = OPCODE_MAP.get(header_num);
if (recv != null) {
    // ... 处理
}
```

**影响：** 每个数据包省掉 ~90 次枚举比较，改为 1 次 HashMap 查找。50 人在线时每秒处理数百个包，累积收益可观。改动范围可控（一个 static 块 + 替换循环体）。

**注意事项：** 需确认 `RecvPacketOpcode.values()` 中无重复的 `getValue()`（opcode 值唯一）。当前代码本身也假设无重复，所以这个前提已成立。

**风险：** 低。HashMap 查找替代线性扫描，语义等价。

### 3. 角色登录查询合并

**文件：** `client/MapleCharacter.java:598-820`

**问题：** `loadCharFromDB()` 对每个登录角色执行 15+ 次独立 DB 查询：

| # | 查询 | 行号 |
|---|------|------|
| 1 | `QDCharacter` findOne | 603 |
| 2 | `QDAchievement` findEach | 635 |
| 3 | `QDQuestStatus` findList | 639 |
| 4-N | `QDQuestStatusMob` findList（每条 quest status 一行）| 656 |
| N+1 | `QDInventorySlot` findOneOrEmpty | 664 |
| N+2 | `ItemLoader.loadItems()` — 内部还有 6 次查询 | 675 |
| N+3 | `QDAccount` findOne | 682 |
| N+4 | `QDQuestInfo` findList | 695 |
| N+5 | `QDSkill` findList | 700 |
| N+6 | `QDCharacter` findList (all chars by account) | 714 |
| N+7 | `QDSkillMacro` findList | 738 |
| N+8 | `QDKeyMap` 内部查询 | ~750 |
| N+9 | `QDSavedLocation` findList | ~760 |
| N+10 | `QDFameLog` 查询 | ~770 |
| N+11 | `QDWishList` findList | ~780 |
| N+12 | `QDTrockLocation` / `QDRegrockLocation` | ~790 |
| N+13 | `DMountData` 查询 | ~800 |

最严重的是 **N+1**：`QDQuestStatusMob` 对每条 quest status 都单独查一次（通常 20-50 条 quest status → 20-50 次 mob 查询）。

**修复方案：**

**快速见效（只修 N+1）：**
```java
// 将 QDQuestStatusMob 改为一次性查全部，按 questStatus 分组
List<DQuestStatusMob> allMobs = new QDQuestStatusMob()
    .questStatus.in(statusList)
    .findList();
// 按 questStatus.hashCode() 分组后分配
```

**中等收益（合并可并行的查询）：**
```java
// 7 个 findList 可以并行发起（EBean 不支持，但可以在同一事务内减少连接获取开销）
// 方案：使用 EBean 的 Transaction 包裹确保在同一连接上执行，减少 commit/roundtrip
```

**高收益但高风险（JOIN 预加载）：**
- 部分查询可以通过 LEFT JOIN 合并到主 DCharacter 查询中（如 quest status、skills）
- 但需要修改 DCharacter 的 EBean 映射，影响范围大

**建议：** 先做快速见效的 N+1 修复（修复 quest mob 查询），不改主查询结构。

**风险：** 低（N+1 修复），中（JOIN 改造）

## 三、次要优化项

### 4. 物品加载 ItemLoader 查询合并

**文件：** `client/inventory/ItemLoader.java`

`loadItems()` 按 6 种背包类型分别查询 `DInventoryEquipment` 和 `DInventoryItem`，可以合并为各一次全查然后按类型分组。

**影响：** 角色登录减少 10 次 DB 查询。

---

### 5. MapleMap 对象池泄露检查

**文件：** `server/maps/MapleMap.java`

地图对象（`MapleMapObject`）在物品消失/怪物死亡后需要从 map 的 object list 中移除。部分临时对象（技能特效、召唤兽）可能未被正确清理，导致 `getMapObjects()` 遍历时包含大量已失效对象。

**影响：** 长期运行的服务器（24h+）地图对象列表膨胀，遍历变慢。

**检查方法：** 在 `getMapObjects()` 中加对象计数日志，观察运行时长与对象数的关系。

---

### 6. 热路径日志检查

多处 handler 在 INFO 级别打印日志（如 `MapleServerHandler.java:477` 每个包都打）。生产环境应将 DEBUG 级别的包内容日志保持 DEBUG，INFO 只打关键事件（登录、登出、错误）。

**当前：** 大多数包日志已是 DEBUG 级别，但个别处（`MapleServerHandler:477`）仍用 INFO。影响不大。

## 四、新增：掉落缓存被 shuffle 破坏

**文件：** `server/maps/MapleMap.java:445-446`

**问题：**

```java
final List<MonsterDropEntry> dropEntry = mi.retrieveDrop(mob.getId());
Collections.shuffle(dropEntry);
```

`retrieveDrop()` 返回的是 `MapleMonsterInformationProvider` 内部缓存的 List（`HashMap<Integer, List<MonsterDropEntry>>`），`Collections.shuffle()` **就地修改**了这个缓存列表。每次怪物死亡，该怪物的掉落顺序就被永久打乱一次。多次击杀后缓存被反复 shuffle，掉落分布扭曲（早期击杀时排在前面的物品概率偏高）。

**修复：**

```java
final List<MonsterDropEntry> dropEntry = new ArrayList<>(mi.retrieveDrop(mob.getId()));
Collections.shuffle(dropEntry);  // 只打乱副本
```

**影响：** 1 行改动，修复掉落缓存的渐进式损坏。所有怪物的掉落分布恢复正常。

**风险：** 极低。ArrayList 拷贝构造是安全的浅拷贝，dropEntry 元素只读不修改。

### 5.1 地图对象泄露检查

对 `MapleMap` 中 11 种地图对象类型的完整生命周期追踪结果：

| 对象类型 | 添加路径 | 移除路径 | 清理机制 | 状态 |
|----------|---------|---------|---------|------|
| MONSTER | `spawnMonster` → `addMapObject` | `killMonster` / `removeMonster` / `killAllMonsters` → `removeMapObject` | 即时 | ✅ |
| ITEM | `spawnMesoDrop/spawnMobDrop` → `spawnAndAddRangedMapObject` | `expire()` / `pickup` → `removeMapObject` | WORLD 定时器扫描 `shouldExpire()` | ✅ |
| PLAYER | `addPlayer` → `characters.add` + `mapobjects.put` | `removePlayer` → `characters.remove` + `removeMapObject` | 即时 | ✅ |
| MIST | `spawnMist` → `spawnAndAddRangedMapObject` | 独立 Timer 调度 → `removeMapObject` | 定时器，独立于施法者 | ✅ |
| SUMMON | `spawnSummon` → `spawnAndAddRangedMapObject` | `removePlayer` 中遍历移除 / 非定点型标记 changedMap 后 removeMapObject | 即时（玩家离图） | ✅ |
| DRAGON | `spawnDragon` → `spawnAndAddRangedMapObject` | `removePlayer` 中 `removeMapObject` | 即时（玩家离图） | ✅ |
| DOOR | `MagicDoor` 技能 → `addMapObject`(target) + `addMapObject`(town) | `cancelEffect` → `isMagicDoor()` → `removeMapObject`(target+town) | 延迟（等 buff 到期） | ⚠️ |
| REACTOR | `respawnReactor` → `addMapObject` | `destroyReactor` → `removeMapObject` (+ Timer 重生) | 即时 | ✅ |
| NPC | `spawnNpc` → `addMapObject` | `removeNpc` / `resetNPCs`（仅自定义 NPC） | 自定义即时，常驻不删 | ✅ |
| SHOP | 玩家开店时添加 | 关店时移除 | 即时 | ✅ |
| HIRED_MERCHANT | 雇佣商店添加 | 到期/关闭时移除 | 即时 | ✅ |

**结论：无永久泄露。** 所有对象类型都有清理路径。

唯一轻微瑕疵：**DOOR 在玩家断线后不会立即移除**——`removePlayer` 中没有调用 `cancelEffectFromBuffStat` 来取消魔法门 buff。门在当前 buff 到期前会一直留在两张地图上（目标图+城镇图）。不影响功能——门到期后 Timer 触发 `cancelEffect` → `isMagicDoor()` 清理。
