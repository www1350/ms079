# 队伍持久化方案

> 将游戏内队伍数据从纯内存缓存改为数据库持久化，服务器重启后自动恢复队伍。

---

## 一、现状分析

### 1.1 当前实现

```
┌─────────────────────────────────────────────────────────────────┐
│                      PartyHandler (创建/加入/退出/踢出/队长转移)   │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│                      PartyService (队伍生命周期管理)              │
│                                                                 │
│  Guava Cache<Integer, MapleParty>                               │
│  ├── createParty()  → 缓存 .put()                               │
│  ├── getParty()     → 缓存 .getIfPresent()                      │
│  ├── updateParty()  → 缓存内修改成员列表                          │
│  └── disbandParty() → 缓存 .invalidate()                        │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                  ┌────────┴────────┐
                  │   MapleParty     │  纯内存对象，Serializable 但从未序列化
                  │   ├── id         │
                  │   ├── leader     │  → MaplePartyCharacter
                  │   └── members    │  → List<MaplePartyCharacter>
                  └─────────────────┘

持久化情况：
  ✅ characters.party 列 (INT) ─── 存角色所属队伍 ID
  ❌ 队伍结构 (队长、成员列表) ─── 无任何持久化，重启即丢失
  ❌ 队伍 ID 生成器 ─── 启动时从 DB 读取 max(party)+2 防碰撞
```

### 1.2 重启后果

| 场景 | 影响 |
|---|---|
| 服务器崩溃/重启 | 所有队伍消失，玩家全部变无队伍状态 |
| 角色重新登录 | `loadCharFromDB()` 尝试按旧 party ID 查缓存，缓存为空 → `party = null` |
| 数据残留 | `characters.party` 列仍保留旧 ID，但对应的队伍已不存在 |

## 二、方案设计

### 2.1 新增数据库表

```sql
CREATE TABLE parties (
  id         INT PRIMARY KEY,
  world_id   INT       NOT NULL DEFAULT 0,
  leader_id  INT       NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_world (world_id),
  INDEX idx_leader (leader_id)
);

-- 迁移时需同步修正 characters.party 中残留的无效引用
UPDATE characters SET party = -1 WHERE party > 0 AND party NOT IN (SELECT id FROM parties);
```

**不加 `party_members` 表**。成员关系由 `characters.party` 列承载——创建/加入时写入，退出/踢出/解散时清除。

### 2.2 新增实体类

```
src/main/java/com/github/mrzhqiang/maplestory/domain/DParty.java
```

标准 EBean Model，映射 `parties` 表。包含 `id`, `worldId`, `leaderId`, `createdAt` 字段。

### 2.3 改动文件清单

| 文件 | 改动 | 说明 |
|---|---|---|
| `db/migration/` 新增 | +1 SQL 文件 | 建表 + 数据清洗 |
| `domain/DParty.java` | 新增 ~30 行 | EBean 实体 |
| `handling/world/MapleParty.java` | +1 构造函数 | 支持从 DB 数据直接构造（指定 leader + 成员列表） |
| `handling/world/MaplePartyCharacter.java` | +几个字段 + setter | 支持离线构造（DB 数据填充） |
| `service/PartyService.java` | ~60 行改动 | 核心：init/CRUD 加 DB 操作 |

总计 **~120 行**净增，不改 `PartyHandler` 和 `MapleCharacter`。

### 2.4 核心改动：PartyService

```
init()
  1. runningPartyId = max(parties.id) + 1  （兼容已有逻辑）
  2. 从 parties 表读取全部队伍
  3. 对每个队伍，查 characters.party = 队伍 ID 的所有角色
  4. 为每个角色构造离线 MaplePartyCharacter（online=false）
  5. 组装 MapleParty 放入缓存
  6. 清理 characters 表中 party 无效引用的残留数据

createParty(chrfor)
  1. 生成 partyId = runningPartyId.getAndIncrement()
  2. 缓存 .put(party)                     ← 已有逻辑
  3. INSERT INTO parties (id, leader_id)  ← 新增
  4. chrfor.saveToDB() (写 party 列)       ← 已有逻辑（在 saveToDB 中）

updateParty(JOIN)
  1. party.addMember(target)              ← 已有逻辑
  2. 成员 saveToDB 写 party 列             ← 已有逻辑

updateParty(LEAVE / EXPEL)
  1. party.removeMember(target)           ← 已有逻辑
  2. 被移除者 saveToDB 设 party=-1         ← 已有逻辑
  3. 如果成员数 == 0 → disbandParty()

updateParty(DISBAND)
  1. 所有成员 party 设为 null              ← 已有逻辑（各成员 saveToDB 清 party）
  2. DELETE FROM parties WHERE id = ?     ← 新增
  3. 缓存 .invalidate()                    ← 已有逻辑

updateParty(CHANGE_LEADER)
  1. party.setLeader(target)              ← 已有逻辑
  2. UPDATE parties SET leader_id = ?     ← 新增

disbandParty(partyid)
  1. DELETE FROM parties WHERE id = ?     ← 新增（确保 DB 同步）
  2. 缓存 .invalidate()                    ← 已有逻辑
```

## 三、启动重建流程

```
服务器启动
    │
    ▼
PartyService.init()
    │
    ├── 1. 查询所有在线世界的 parties
    │      new QDParty().findList()
    │
    ├── 2. 对每个 party:
    │      ├── 查 QDCharacter().party.eq(partyId).findList()
    │      ├── 构造 MaplePartyCharacter 列表（online = false）
    │      ├── 找出 leader（leader_id 匹配 + 兜底逻辑）
    │      └── new MapleParty(id, leader, members) → 放入缓存
    │
    ├── 3. 清理残留:
    │      UPDATE characters SET party = -1
    │      WHERE party > 0 AND party NOT IN (SELECT id FROM parties)
    │
    └── 4. runningPartyId.set(maxId + 1)
    │
    ▼
角色登录时
    │
    ▼
loadCharFromDB()
    ├── 从 characters.party 读 partyId
    ├── World.Party.getParty(partyId) → 缓存命中（已重建）
    ├── chr.setParty(party)
    └── updateParty(LOG_ONOFF) → 更新 online 状态 + 最新角色数据
```

### 关键设计点

1. **离线成员保留**：队伍中有角色不在线时队伍仍然存在，`online=false` 标记。成员登录时通过 `LOG_ONOFF` 更新在线状态和角色数据。

2. **队长兜底**：如果 `leader_id` 对应的角色已不在队伍中（legacy 数据），取成员列表中等级最高者为队长。

3. **脏数据自愈**：`init()` 末尾清理 `characters.party` 中指向不存在队伍的残留数据，保证数据一致性。

4. **不改 PartyHandler**：持久化逻辑完全封装在 `PartyService`，Handler 层无感知。

## 四、边界场景处理

| 场景 | 处理方式 |
|---|---|
| 队长退出/离线 | `updateParty` 已自动选择等级最高者继任队长（现有逻辑，不变） |
| 队长被踢 | 同上，自动继任 + DB 更新 leader_id |
| 队伍自动解散（人数 ≤0） | `updateParty` 末尾检查 `members.size() <= 0` → `disbandParty()` |
| 所有成员离线 | 队伍保留在 DB + 缓存中，`online=false` |
| DB 中 party ID 冲突 | `runningPartyId` 从 max+1 开始，旧 ID 不会被复用 |
| 角色删号 | EBean cascade 或手动清理：角色被删时检查并清理队伍 |
| 跨世界队伍 | `parties.world_id` 隔离，同一队伍只在单世界内有效 |

## 五、数据库迁移

```sql
-- migration/V0001__add_parties_table.sql

CREATE TABLE IF NOT EXISTS parties (
  id         INT PRIMARY KEY,
  world_id   INT       NOT NULL DEFAULT 0,
  leader_id  INT       NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_world (world_id),
  INDEX idx_leader (leader_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 清理历史残留：party 值指向不存在的队伍的角色
UPDATE characters SET party = -1 WHERE party > 0;
```

> 迁移时将所有历史 `party > 0` 统一置为 -1，因为旧的队伍结构数据已不可恢复。新队伍从迁移后才开始持久化。
